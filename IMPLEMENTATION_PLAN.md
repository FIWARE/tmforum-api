# Implementation Plan: TMForum - DB Backend - Query Translation

## Overview
Split `common/.../querying/QueryParser` at an explicit AST boundary. A backend-neutral query model in `storage-api` (filter tree, value types, sort keys) is produced by the TMForum-syntax front half and rendered by two permanent renderers: the existing NGSI-LD `q`/`orderBy` renderer, and a new JSONB/SQL renderer in `storage-postgresql`. The storage port then takes the model instead of NGSI-LD strings, and `PostgresEntityRepository` gains filtering, ordering and pagination (always `WHERE is_current`). The steps end with the filter, sort and paging ITs passing on PostgreSQL, Orion-LD and Scorpio.

Ground rules for every step:
- Keep the NGSI-LD ITs green after every step. The NGSI-LD renderer stays permanent and is tested on equal footing (decision 7).
- Do not change TMForum filter syntax or semantics. `SubscriptionQueryResolver` stays out of scope.
- No index tuning (decision 12). Bind every user value as an SQL parameter and never concatenate one into SQL.
- A behaviour difference between the backends either reaches parity or becomes a deviation, and only a human accepts a deviation; recording it does not. The step that observes a deviation pins it as a `KnownDeviation` entry whose Javadoc says "pending acceptance (ticket 0)", and lists it (backend, version, behaviour) under a `Deviations for acceptance` heading in its completion `taiga_comment` so a human can accept it into ticket 0's table. Only an accepted deviation drops the "pending" note and gets a line in `release-notes/RELEASE_NOTES_POSTGRESQL_ADAPTER.md`. Never design a deviation in up front; where the plan needs a decision, it says so and defaults to parity.
- Doc density stays sparse (see AGENTS.md). Use named constants and parameterized tests.

## Steps

### Step 1: Backend-neutral query model in `storage-api`
Add the package `org.fiware.tmforum.storage.query` in `storage-api/src/main/java`. It holds plain Java records and enums with no dependencies, because the enforcer bans `io.github.wistefan`, `io.micronaut` and `org.fiware.tmforum` there:
- `ValueType` {`STRING`, `NUMBER`, `BOOLEAN`, `DATE_TIME`}. The first three are the neutral twins of the mapping library's `QueryAttributeType`, which `storage-api` must not see. `DATE_TIME` has no twin there (the library reports dates as `STRING`); it marks a declared date-time attribute so that a renderer can pick a date-time comparison. Whether one does is decided after Step 2 (see "Date-time gate" below): byte order of ISO strings is wrong across precisions and offsets (`…00.500Z` < `…00Z`, since `.` < `Z`), but string comparison may be exactly what the brokers do today.
- `DateTimeLiterals`, a small `java.time`-only helper: `Optional<OffsetDateTime> parse(String)` accepts an ISO-8601 date-time with offset or `Z`, a local date-time (read as UTC) and a date (start of day UTC). Both halves use it: the front half to pick `DATE_TIME` (Step 2), the JSONB renderer to bind the literals (Step 4).
- `ComparisonOperator` {`EQUALS`, `GREATER_THAN`, `GREATER_THAN_EQUALS`, `LESS_THAN`, `LESS_THAN_EQUALS`, `REGEX`}. There is no not-equals: the regex not-equals rewrite is an NGSI-LD renderer optimisation (Step 2).
- `AttributePath(List<String> segments, boolean declared)`. The segments are the TMForum path after JSON-LD reserved-token translation (`@type` → `atType`, ...), i.e. the Java bean property names that `getNGSIAttributePath` resolves. They are neither the NGSI-LD attribute names nor necessarily the storage keys; each renderer maps them to its own layout (Steps 2 and 4). `declared == false` marks a free-form extension attribute.
- `QueryFilter`, a sealed interface with `Comparison(AttributePath attribute, ComparisonOperator operator, ValueType valueType, List<String> values)` (values OR-ed, already validated and trimmed for their type; each value is one exact literal that no renderer splits further; a `REGEX` comparison carries exactly one pattern, see Step 2), `AllOf(List<QueryFilter>)` and `AnyOf(List<QueryFilter>)`.
- `SortKey(AttributePath attribute, ValueType valueType, boolean descending)`. `valueType` is null for an undeclared (extension) attribute: a sort has no literal to infer a type from.
- `EntityQuery(Class<?> queryClass, QueryFilter filter, List<SortKey> sort)`. `filter` may be null, and `sort` is empty when there is no sort. `queryClass` is the class paths were resolved against; the NGSI-LD renderer needs it for `findEntitiesPolymorphic`, which has no entity class.

The compact constructors reject null or empty lists where they make no sense, and copy lists immutably. Records give `equals`/`hashCode`, which matters if a call ever becomes a cache key.

Do not change the port yet. Add a unit test in `storage-api/src/test/java/.../query/` (parameterized) for the constructor invariants.
Acceptance: `mvn -pl storage-api verify` passes, enforcer included.

### Step 2: Split `QueryParser` into parse and NGSI-LD render (NGSI-LD output unchanged for every existing test)
In `common/src/main/java/org/fiware/tmforum/common/querying/`:
- **Front half, `QueryParser`.** Add `ParsedQuery parse(Class<?> queryClass, String queryString)` returning `ParsedQuery(String ids, String types, QueryFilter filter)`, and `List<SortKey> parseSort(Class<?> queryClass, Map<String, List<String>> parameters)`. The parse moves here unchanged:
  - well-known-parameter removal and the AND(`&`)/OR(`;`) split, including the "combining is not supported" `QueryException`;
  - `parseParameter`/operator detection, OR-grouping per attribute and operator (`combineParts`), and `,`-value splitting (never for `.regex`);
  - JSON-LD reserved-token translation, the `id`/`type` shortcuts into `ids`/`types`, and attribute type resolution through `JavaObjectMapper.getNGSIAttributePath`. An empty path means `declared = false`, with the type inferred as in today's `getPathToAdditionalAttributes`: once per comparison, from the combined value after `combineParts` and before any value split. So `ext=1` is `NUMBER`, while `ext=1,2`, `ext=1;ext=2` and a mixed `ext=1,abc` are `STRING` (the combined `1,2` is no number), which keeps today's `ext=="1","2"` output. Do not infer per split literal: that changes the NGSI-LD output of multi-value extension filters;
  - all validation (`validateOperator`, the boolean/number literal checks), so both backends answer the same 400s.
- **Semantics the front half fixes** (so the renderers cannot drift apart):
  - *Date-time.* When the resolved path ends at a declared field of a date-time Java type (`Instant`, `OffsetDateTime`, `ZonedDateTime`, `Date`), the type is `DATE_TIME`, resolved from the getter's return type, not from `QueryAttributeType`. It is `DATE_TIME` only if every literal parses through `DateTimeLiterals` (offset or `Z`, local date-time, date); otherwise the comparison stays `STRING`, as today. No new 400: the ticket keeps TMForum filter semantics out of scope, and `lastUpdate.gt=2024-01-01` keeps working on the brokers. The model keeps the literal as given, and the NGSI-LD renderer renders `DATE_TIME` exactly like `STRING`, so its `q` output is unchanged. The front half is the only authority on `ValueType`: it reads the leaf getter's return type during the same declared-getter walk that `getNGSIAttributePath` does (the mapping library's resolution). `DocumentPathResolver` (Step 4) only maps names to document keys and never decides a type, so the two walks cannot disagree on a type. `.regex` on a date-time field yields a `STRING` comparison that matches the stored string. `validateOperator` keeps checking against the mapping library's `QueryAttributeType`, which reports dates as `STRING`, so `.regex` stays allowed there; do not move that check onto `ValueType`.
  - *Regex OR.* `combineParts` keeps joining OR-ed regex values with `,`, and regex values are never split. So `a.regex=x;a.regex=y` stays one literal pattern `x,y` on every backend, as on the brokers today. A `REGEX` comparison therefore always has exactly one value. Do not change this here.
  - *Separators inside a value.* The split in `encodeStringValue` moves to the front half. A parsed string value that contains `ngsildOrQueryValue` becomes separate OR-ed values, so `name=a|b` (with `|` configured) matches `a` or `b` on every backend, PostgreSQL included. With the default `,` this never happens, because the front half has already split on `,`. The `;` branch is unreachable from parsed input, since `;` already separated the parameters. After this, a model value is always one exact literal, and the NGSI-LD renderer quotes it without splitting. Callers that build a `Comparison` directly (the hub check, Step 3) can then pass a URL containing `,`, `;`, `|` or `&` safely. No `QueryParserTest` case has a separator inside a value, so they all stay byte-identical. Only a value containing a non-default separator under `includeAttributeInList=true` renders differently (`(name=="a"|name=="b")` instead of `name==("a"|"b")`), with the same meaning; add a renderer test for it.
  - *Relationship without `.id`.* A filter path that is exactly a relationship attribute (`productSpecification=urn:...`, `isRelationship` on a one-segment path) gets `id` appended, so the model always points at the referenced id. The NGSI-LD renderer strips a trailing `.id` on relationships anyway, so its output is unchanged, and the JSONB renderer needs no relationship flag. Sort paths are not normalised, because today's `orderBy` keeps them as given.
  - *Undeclared sort keys* get `valueType == null` (see Step 1).
  - *Path segments stay TMForum names.* The model keeps the path as the client wrote it (after reserved-token translation), not the resolved NGSI-LD path, so the NGSI-LD renderer resolves it through `getNGSIAttributePath` exactly as today and its output stays unchanged. Do not store the NGSI-LD path in the model: it is not the PostgreSQL key either (see Step 4).
- **Back half, new `NgsiLdQueryRenderer` (`@Singleton`, takes `GeneralProperties`).** It provides `String renderFilter(EntityQuery)` and `String renderOrderBy(EntityQuery)`. Everything NGSI-LD moves here: the NGSI path through `getNGSIAttributePath`, `isRelationship`, `escapePath`/reserved-word escaping, the `.id` stripping for relationships, `mapPathPart` (`useDotSeperator`), `encodeValue`/`encodeStringValue`, `includeAttributeInList`/`encloseQuery`/`ngsildOrQueryKey`/`ngsildOrQueryValue`, the operator symbols (`Operator.getNgsiLdOperator`), the `;desc` suffix and `applyRegexNotEqualsOptimization`.
- Keep `toNgsiLdQuery(...)` and `toOrderBy(...)` for now as thin façades (`parse` + render, still returning `QueryParams`), so no caller changes in this step.
- **Pitfall: output order.** Today's OR grouping uses `Collectors.toMap` (HashMap iteration order), and the `QueryParserTest` expectations depend on it (e.g. `color==\"Red\"|(status...)`). Keep the same grouping so every existing `QueryParserTest` case stays byte-identical. Do not "fix" the order here.
- Tests:
  - `QueryParserTest` stays unchanged and green.
  - Add `QueryParserModelTest`, parameterized TMForum string → expected `EntityQuery`/`ParsedQuery`, covering reserved tokens, extension attributes (`ext=1` → `NUMBER`, `ext=1,2` and `ext=1,abc` → `STRING` with two values), regex with `,` and with `;`-OR, `DATE_TIME` resolution (offset, `Z`, local date-time, date-only, and the `STRING` fallback for a non-date literal), the `ngsildOrQueryValue` split inside a value, relationship `id` normalisation, renamed attributes (`otherNamedSub.status` keeps the segment `otherNamedSub`, not `otherSub`), undeclared sort keys, and the 400 cases.
  - Add `DateTimeFilterBehaviourIT` in product-catalog, a characterisation IT that runs only on the brokers (`-Dbroker=orion-ld` and `scorpio`); gate it with the existing `@BrokerOnly`. It seeds product offerings whose `lastUpdate` is stored with and without a fraction (`…00Z`, `…00.500Z`). `ProductOfferingApiController` overwrites `lastUpdate` with `clock.instant()` on create and patch, so a `lastUpdate` in the request body is lost: replace the `Clock` with `@MockBean(Clock.class)` as `ProductOfferingApiIT` does and stub `clock.instant()` per create (`Instant.toString()` writes a zero fraction as `…00Z`). Assert after seeding that the stored values differ in precision, so uniform data cannot pass unnoticed. It then filters and sorts on `lastUpdate` with literals in `Z`, `+01:00`, local date-time and date-only form, across `eq`/`gt`/`gte`/`lt`/`lte`. It asserts what each broker returns today, i.e. whether it compares instants or strings. Report the observed table (broker, version, literal form, result) in the step's completion comment as input for the date-time gate.
  - Add `NgsiLdQueryRenderer` tests over hand-built models for every `GeneralProperties` combination already covered by `QueryParserTest`, plus a value containing `,`, `;`, `|` and `&` that must come out as one quoted literal.
    - One intended NGSI-LD output change: today `applyRegexNotEqualsOptimization` passes the `X` of `^(?!X$).*$` through `encodeStringValue`, which splits it, so `name.regex=^(?!a,b$).*$` renders `name!="a","b"` (not a nor b). Once a value is one literal, it renders `name!="a,b"`, which is what the regex means. Pin the new output in an `NgsiLdQueryRenderer` test (with the default `,` and with a configured `|`) and name it in the step's completion comment as the one deliberate change; no existing `QueryParserTest` case covers it.

Acceptance: `mvn -pl common -am test` is green, the NGSI-LD output of every existing test case is unchanged, and `DateTimeFilterBehaviourIT` is green on Orion-LD and Scorpio with its observations reported.

### Date-time gate (between Step 2 and Step 4)
Step 2's `DateTimeFilterBehaviourIT` decides how the JSONB renderer compares `DATE_TIME` (Step 4); the ticket keeps TMForum filter semantics out of scope, so parity with the brokers is the default:
- **Both brokers compare instants** for every literal form: render instants on PostgreSQL (the `timestamptz` variant in Step 4). That is parity, no decision needed.
- **A broker compares strings** (for some or all literal forms): render `DATE_TIME` on PostgreSQL as the broker does, i.e. as a `STRING` comparison (`COLLATE "C"`) for those forms, so a mixed-precision filter is as wrong as on the broker. Step 2 lists instant semantics as a proposed deviation under `Deviations for acceptance`. Step 4 implements the `timestamptz` variant only if a human has accepted it into ticket 0 by the time Step 4 starts (a comment on this ticket); without that, it implements string parity and leaves the instant variant out.
- **The brokers disagree with each other:** follow the human decision on the ticket; without one, match Orion-LD, today's default backend, and record the Scorpio difference as a pending deviation.

Steps 6 and 7 assert whatever the gate chose, on every backend; the mixed-precision seeds stay so the choice is pinned.

### Step 4: JSONB/SQL renderer in `storage-postgresql`
Add `JsonbQueryRenderer` (package-private or a plain class; no bean needed) in `storage-postgresql/src/main/java/.../postgresql/`. It renders an `EntityQuery` into `SqlFragment(String sql, List<Object> bindings)`, starting at a given parameter index, for both the `WHERE` part and the `ORDER BY` part. It works against `data` of `tmforum.entity`. Keys are the domain property names, because `PostgresDocumentMapper` pins the naming; dates are ISO-8601 strings; extensions are top-level keys (`PostgresMappingModule`).

Suggested shape (the step agent may refine it, but must keep bind parameters and type-correct comparisons):
- **Path.**
  - Build a lax jsonpath with each segment as a quoted, escaped (`"` and `\`) member accessor followed by `[*]`, e.g. `$."relatedParty"[*]."role"[*]`. In lax mode `[*]` unwraps arrays and wraps scalars, so list-valued references (inline per ticket 5), lists of strings (`entities`, `eventTypes`) and plain values all behave as "any element matches", like NGSI-LD.
  - Bind the jsonpath text as a parameter (`$n::jsonpath`); it is never concatenated into the SQL.
  - **Storage keys.** A declared path's segments are TMForum (Java bean) names, and the document is keyed by Jackson property names. They usually match, but not always, so resolve each declared segment to its document key before building the jsonpath. Use neither the segment as-is nor the NGSI-LD path; each is wrong for some case in the codebase:
    - `Customer.characteristic`, `Individual.location`, `ResourceFunction.connectivity` and `MyPojo.otherNamedSub` have a different NGSI-LD `targetName` (`characteristics`, `individualLocation`, `resourceGraph`, `otherSub`), but their document key is the TMForum name.
    - `AppliedBillingRateCharacteristic.value` is a `@JsonIgnore`d bridge getter with `@AttributeGetter(targetName = "tmfValue")`. The TMForum path `characteristic.value` must become the document key `tmfValue`; a jsonpath on `value` silently matches nothing.

    Add a `DocumentPathResolver` in `storage-postgresql`, built on the `PostgresDocumentMapper` `ObjectMapper` (the one that writes the documents). It walks `EntityQuery.queryClass` through Jackson's serialization introspection: per segment, take the serialized property of that name and descend into its type (the content type for collections and arrays). If the bean property is not serialized, take the getter's `@AttributeGetter.targetName` when that names a serialized property (the bridge case). If a segment still does not resolve (e.g. a subtype-only field in a polymorphic query), keep it as-is. Cache per class and path. Sort keys go through the same resolver.
  - Undeclared (extension) attributes use their segments as-is from the top level. Do not apply NGSI-LD reserved-word escaping (`tmfEscaped-...`); that is a broker-only artefact.
- **Comparison.** Use `EXISTS (SELECT 1 FROM jsonb_path_query(data, $n::jsonpath) AS v(value) WHERE <predicate>)`, with a predicate per `ValueType`:
  - `STRING`: `jsonb_typeof(v.value) = 'string'`, then `v.value #>> '{}' = ANY($m::text[])` for equality, or `(v.value #>> '{}') COLLATE "C" <op> ANY($m::text[])` for ordering. `COLLATE "C"` gives byte order, the closest match to the brokers.
  - `NUMBER`: `CASE WHEN jsonb_typeof(v.value) = 'number' THEN (v.value)::numeric END <op> ANY($m::numeric[])`. Guard it with `CASE` for the same reason as `DATE_TIME` below: `(jsonb)::numeric` on a string or object raises an error that fails the whole list, and `AND` gives no evaluation order. This is realistic: an extension attribute gets `NUMBER` from a literal (`foo=5`) while other entities store `"foo": "abc"`. A non-number then matches nothing.
  - `BOOLEAN`: `v.value = ANY(...)` over `to_jsonb` booleans.
  - `DATE_TIME`: render it as the date-time gate decided. With string parity it is the `STRING` predicate above. The instant variant (only on parity with the brokers or an accepted deviation) is `<ts> <op> ANY($m::timestamptz[])`, with the literals parsed through `DateTimeLiterals` and bound as `OffsetDateTime`. Equality compares instants, so `…00Z` equals `…00.000Z` and `…01:00+01:00`.
    - `<ts>` is a guarded cast: `CASE WHEN jsonb_typeof(v.value) = 'string' AND pg_input_is_valid(v.value #>> '{}', 'timestamptz') THEN (v.value #>> '{}')::timestamptz END` (k3s runs `postgres:18`; `pg_input_is_valid` exists since 16). Use `CASE`, not `AND`, because PostgreSQL does not promise to evaluate `AND` operands in order.
    - The guard matters. Stored data is not only what this mapper wrote: ticket 8 migrates broker data, and a polymorphic query resolves the path against the query class while a subtype can hold another shape there. Without it, one unparseable value aborts the whole list with a 500. With it, such a value matches nothing and sorts as NULL. Cover it in `PostgresQueryRenderingIT`.
    - Pin the session `TimeZone` to `UTC` so stored strings without an offset read as UTC, the same rule `DateTimeLiterals` applies to literals. The connections are pooled (`r2dbc:pool:`), so never `SET TimeZone` per statement: it would leak to the next borrower of the connection and is easy to forget on the count statement. Set it once per connection through r2dbc-postgresql's `timeZone` connection option, which otherwise defaults to the JVM time zone. Prefer setting it in code in `storage-postgresql` (a customisation of the connection factory options Micronaut R2DBC builds), so no deployment yaml can omit it; if Micronaut R2DBC offers no such hook, add the option to the `r2dbc.datasources.default` block of every module's main and test `application-postgresql.yaml`. Verify that the chosen form reaches the driver: an IT in `storage-postgresql` runs with a non-UTC JVM default (`-Duser.timezone=Europe/Berlin` on that IT, or `TimeZone.setDefault` before the context starts) and asserts `current_setting('TimeZone') = 'UTC'` on every connection the pool hands out (borrow more than one).
    - `timestamptz` keeps microseconds, so a sub-microsecond `Instant` compares rounded. That is harmless; note it in the release notes (Step 7).
  - `REGEX`: `jsonb_typeof(v.value) = 'string' AND (v.value #>> '{}') ~ $m`. PostgreSQL ARE supports lookahead, so the not-equals idiom `^(?!X$).*$` works natively. There is exactly one pattern per comparison (Step 2).
  - `AllOf`/`AnyOf` become parenthesised `AND`/`OR`.
- **Sort.** Render `ORDER BY <expr> ASC|DESC` per key, with `<expr>` = `jsonb_path_query_first(data, $k::jsonpath)`, typed as above (`#>> '{}' COLLATE "C"` for strings, the same `CASE`-guarded `::numeric` cast for numbers, and for `DATE_TIME` whatever the date-time gate chose: the string expression or the guarded `timestamptz` cast). A key with `valueType == null` (undeclared) orders by the raw `jsonb` value, which PostgreSQL orders across types with a defined rule; if the brokers order such keys differently, record a deviation in Step 6. Always append `created_at, id` as a tiebreaker so paging stays stable. Choose the NULLS placement to match the brokers once Step 7 observes them, defaulting to `NULLS LAST`.
- Put SQL fragments in named constants and reuse no magic strings.
- Tests: `DocumentPathResolverTest` (parameterized) over test types with a different NGSI-LD `targetName` (key stays the bean name), a `@JsonIgnore`d bridge getter (key becomes the `targetName` property), a nested list element type and an unresolvable segment. `JsonbQueryRendererTest` (parameterized: model → expected SQL plus bindings) for every operator × value type, AND/OR nesting, nested paths, extension attributes, quoting of segments containing `"`/`.`/`\`, `DATE_TIME` as the gate chose it (sub-second vs whole-second, `Z` vs offset, date-only and local literals), and sort, including an undeclared sort key. Add a renderer-level `PostgresQueryRenderingIT` in `storage-postgresql/src/test` that executes the fragments against the k3s PostgreSQL over seeded raw documents (scalars, arrays, nested arrays, missing keys, mixed types, a non-date string and a number at a `DATE_TIME` path, a string and an object at a `NUMBER` path, in both filter and sort, an invalid regex). Check the document-level semantics there, independent of the domain mapping.

Acceptance: `mvn verify -pl storage-postgresql` is green.

### Step 5: Filtering, ordering and pagination in `PostgresEntityRepository`
- Remove `LIST_NOT_SUPPORTED` and wire `JsonbQueryRenderer` into `list(...)`. The predicate is `WHERE is_current AND type = ANY($1)` [`AND id = ANY($2)`] `AND <filter>`; then `ORDER BY <sort keys>, created_at, id` (only `created_at, id` without sort keys); then `LIMIT`/`OFFSET`. Renumber the parameters after the rendered bindings.
- `totalCount`'s fallback `COUNT` query must use the same predicate, filter and `is_current` included.
- A pattern PostgreSQL's ARE rejects raises SQLSTATE `2201B` (`invalid_regular_expression`), which `PostgresFailures` maps to nothing today, so the client would get a 500 where the brokers answer 400. Map `2201B` on the list and count path to `QueryException` (400 through `QueryExceptionHandler`; `storage-postgresql` already depends on `common`), as a named constant next to `UNIQUE_VIOLATION`. Test it in `PostgresFailuresTest` and with an unbalanced pattern (`(`) in `PostgresEntityRepositoryIT`.
- The 2201B mapping alone makes the 400 depend on the data: `~` compiles a bound pattern only when a row reaches the predicate, so with no entity of the type, or none holding the path, the request answers 200 with an empty list. Validate every `REGEX` pattern of the filter up front instead: run `SELECT '' ~ $1` per distinct pattern on the same connection before the list and count statements, and map its 2201B to `QueryException`.

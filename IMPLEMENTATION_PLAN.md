# Implementation Plan: TMForum - DB Backend - Entity versioning

## Overview
This plan gets the PostgreSQL schema ready for entity versioning and adds the one behaviour the ticket asks for, reference version semantics. Ticket 6 already created `version`/`revision`/`is_current`, `PRIMARY KEY (id, version)` and `entity_current_idx`, and every read, update and delete already filters `AND is_current`. Two things are missing. The `version` column is never filled, so it is always `''`. And no reference check looks at a `*Ref`'s `version`. No API surface is added. `PATCH` keeps updating in place, and both backends behave the same.

**Decisions taken by this plan** (the step agents apply them, they do not reopen them):
- A type is *versionable* when its domain class implements a new marker interface `VersionedEntity` (`String getVersion()`). The 18 classes listed in the ticket implement it, and Lombok already generates the getter. Their subclasses inherit it: the 7 TMF730 `ResourceSpecification` sub-types (`ResourceTypeRegistry.SPEC_ENTITY_TYPES`) each store their own entity type and inherit `version`, so they are versionable too. That makes 25 versionable stored types today: every `@MappingEnabled` entity type of a class that is a `VersionedEntity`, subclasses included. A `version` that is null or comes from any other class is stored as `''`. A key found in the document is not used, because an extension property called `version` on a non-versionable type would otherwise fill the column.
- Both adapters derive a target's version the same way: its label when the stored type is versionable, `''` otherwise. PostgreSQL decides by the class (`VersionedEntity`) at write time. The broker adapter only sees the stored NGSI-LD type, so it decides by `VersionedEntity.VERSIONED_TYPES`, the set of those 25 stored type names. A guard test keeps that set equal to the classes, and fails when a class with a `version` attribute does not implement `VersionedEntity`. A non-versionable entity with an extension `version` therefore reports `''` on every backend, and a pinned ref to it is rejected everywhere.
- PostgreSQL rows written before this ticket have `version = ''` while `data` holds the label, because the backend is already selectable through the `postgresql` profile. A Flyway migration backfills them, so a pinned ref to such a row behaves as it does on the broker.
- A `*Ref` is *version-pinned* when its `version` is non-null and non-empty. A pinned ref resolves only if the target's current version equals it exactly (case-sensitive, no trimming). An unpinned ref resolves whatever version the target has.
- A pinned ref whose target type has no version (the target's version is `''`) is a mismatch and is rejected. Examples are `ConnectionPointRef`, `ResourceFunctionRef`, `ServiceLevelSpecificationRef` and `ConstraintRef`. Both backends do the same, so this is not a deviation.
- The version is compared whenever a stored target is found, in both scopes. A `LOCAL` ref and an `EXTERNAL` ref whose id names a local entity (ticket 4 already type-checks that case) are both rejected on a version mismatch, so a wrong version cannot be smuggled in through an external href. An `EXTERNAL` ref with no local target is still skipped, version-agnostic.
- A version mismatch is reported through the existing `NonExistentReferenceException` path (HTTP 400). The message is separate (`Reference version mismatch: ...`), and the reference counts as `unresolved` in the `tmforum.references` metric.
- `revision` and `is_current` are left to their column defaults (`1`, `true`). They are not bound in the `INSERT`. Tests check the stored values.

## Steps

### Step 1: Fill the `version` column on every PostgreSQL write
Write the TMForum `version` label into `tmforum.entity.version` on create, import and update. Before this step it always stays `''`.

- **`common/src/main/java/org/fiware/tmforum/common/domain/VersionedEntity.java`** (new): a marker interface `String getVersion()` with a one-line Javadoc. It marks the entity types whose `version` labels a stored row. It also holds `Set<String> VERSIONED_TYPES`, the 25 versionable stored type names (the 18 classes' types plus the 7 `ResourceSpecification` sub-types: `logical-resource-specification`, `physical-resource-specification`, `software-resource-specification`, `api-specification`, `software-specification`, `hosting-platform-requirement-specification`, `software-support-package-specification`) as string literals (`common` cannot see the module classes), for adapters that only know a stored type.
- Add `implements VersionedEntity` to the 18 domain classes. Do not change their fields or annotations: `agreement/.../domain/{Agreement,AgreementSpecification}.java`, `document-management/.../domain/DocumentSpecification.java`, `product-catalog/.../domain/Catalog.java`, `product-shared-models/.../product/{Category,ProductOffering,ProductOfferingPrice,ProductSpecification,Quote}.java`, `resource-catalog/.../domain/ResourceCatalog.java`, `resource-shared-models/.../resource/{ResourceCandidate,ResourceCategory,ResourceSpecification}.java`, `service-catalog/.../domain/ServiceCatalog.java`, `service-shared-models/.../service/{ServiceCandidate,ServiceCategory,ServiceSpecification}.java`, `usage-management/.../domain/UsageSpecification.java`. Confirm the list with `grep -rl 'targetName = "version"' --include=*.java . | grep -v Ref.java | grep -v /target/`. That grep only finds classes that declare the attribute, not ones that inherit it. The 7 `ResourceSpecification` sub-types in `resource-shared-models` inherit both `version` and `implements VersionedEntity`, need no edit, and are listed in `ResourceTypeRegistry.SPEC_ENTITY_TYPES`. Find other subclasses with `grep -rn 'extends <Class>\b'` for each of the 18, or rely on the guard below.
- **`storage-postgresql/.../PostgresEntityRepository.java`**:
  - `INSERT` gets a `version` column and parameter. `bindInsert` binds `versionOf(entity)`, a private static helper that returns `VersionedEntity.getVersion()` or `""` when the entity is not versioned or the version is null. Name the constant (for example `UNVERSIONED = ""`). This covers `createDomainEntity`, `importDomainEntity` (migration) and `createWithEvent`.
  - `UPDATE_CURRENT` and `UPDATE_CURRENT_RETURNING_DATA` get `version = COALESCE($3, version)`. The patch binds its own `getVersion()` when it is a non-null `VersionedEntity`, otherwise a typed null (`bindNullable(..., String.class)`). An update that does not carry `version` leaves the column alone. A carried `version` moves the column with `data`, in place on the same row, and that changes the primary key, which PostgreSQL allows.
  - Do not add a `version` predicate to reads. They stay `WHERE id = $1 AND is_current`.
- **`storage-postgresql/src/main/resources/db/migration/tmforum/V3__entity_version_backfill.sql`** (new): `UPDATE tmforum.entity SET version = data->>'version' WHERE is_current AND version = '' AND type IN (<the 25 names of VERSIONED_TYPES>) AND COALESCE(data->>'version', '') <> ''`. Only one row exists per id, so the changed primary key cannot collide.
- **Guard** (`all-in-one/src/test/java/org/fiware/tmforum/VersionedTypesTest.java`, next to `RelationshipsReadFromPropertiesTest`, reusing `RelationshipTargets.classes()`):
  - the `@MappingEnabled(entityType)` values of every scanned class that is assignable to `VersionedEntity`, subclasses included, equal `VersionedEntity.VERSIONED_TYPES` (25 today), and equal the type list in `V3__entity_version_backfill.sql` (read as a classpath resource, quoted names extracted);
  - every scanned `EntityWithId` subclass whose public methods (`Class#getMethods`, so inherited getters count) include one annotated `@AttributeGetter(targetName = "version")` is assignable to `VersionedEntity`. A future entity with a `version` attribute that forgets the interface fails here instead of silently storing `''`. Step 3's `RefEntity` guard is the counterpart on the `*Ref` side.
- **Tests** (`storage-postgresql/src/test/...`):
  - In `DocumentTestEntities`, add a versioned test entity that implements `VersionedEntity`.
  - `PostgresEntityRepositoryIT` gets a parameterized case over (versioned with version, versioned with null version, unversioned). After create or import, read the row's `version`, `revision` and `is_current` directly with SQL and expect (`label`/`''`/`''`, `1`, `true`).
  - Cases for update: an update that carries a new version moves the column, an update without version keeps it, and there is still exactly one current row per id.
  - `PostgresEntityRepositoryTest`: unit-level checks of the bound parameters if that file already covers statements this way.
  - `SchemaMigrationIT` already confirms the DDL. Leave its existing assertions unchanged. Add a backfill case: insert rows with `version = ''` before V3 runs (or run V3's statement on them), one of a versionable type with `data.version`, one of a `ResourceSpecification` sub-type (for example `logical-resource-specification`) with `data.version`, one of a non-versionable type with an extension `data.version`. Expect the label on the first two and `''` on the third.
- **Acceptance:** `mvn test -pl storage-postgresql -am` and `mvn test -pl all-in-one -Dtest=VersionedTypesTest` pass, as does `mvn verify -pl storage-postgresql` (its ITs). The full build compiles (`mvn clean install -DskipTests -DskipITs`).

### Step 2: Carry the target's current version in `StoredReference`, filled by both adapters
Give the reference port the target's current `version`, so validation can compare a reference's version with it.

- **`storage-api/.../StoredReference.java`**: change it to `record StoredReference(String id, String type, String version)`. Update the Javadoc: `version` is the current version label, `''` for an unversioned type, never null. A compact constructor maps null to `''`. Update every `new StoredReference(` caller. There are about 12, in main and test code (`grep -rn "new StoredReference(" --include=*.java . | grep -v /target/`). Do not keep a 2-argument constructor, so the compiler catches any adapter that forgets the version.
- **`storage-postgresql/.../PostgresReferencesRepository.java`**: `SELECT id, type, version ... WHERE id = ANY($1) AND is_current`, and map the new `VERSION_COLUMN`.
- **`common/.../repository/BrokerBackedReferencesRepository.java`**: in `findReference`, read the `version` property from the retrieved `EntityVO` (`getAdditionalProperties()`, a `PropertyVO` value, `toString`). It is `''` when the property is absent, and also `''` when `VersionedEntity.VERSIONED_TYPES` does not contain `entityVO.getType()`, even if the entity carries an extension `version`. This keeps the broker in line with PostgreSQL. `retrieveEntityById` already returns the full entity through the 2 s entities cache, so no extra round trip happens. Check in an IT which compacted key the broker returns for `version` (Orion-LD and Scorpio, with the core context link header). If the key is escaped like other reserved names, use the same escaping helper the repositories already use.
- **Contract** (`storage-api/src/test/.../contract/`):
  - Add `VersionFixture<T> extends EntityFixture<T>` with `T withVersion(URI id, String version)`. Implement it in `product-catalog/src/test/.../storage/CatalogFixture.java` (Catalog is versionable).
  - In `AbstractReferenceReadRepositoryContractTest`, add a parameterized case where an entity created with version `v` is reported by `findReference` and `findReferences` with version `v`, and an entity created without one is reported with `''`. Also add a case that updates the version and then expects `findReference` to report the new version. Skip these cases (`assumeTrue`) when the fixture is not a `VersionFixture`, following how `referenceFixture()` is optional.
  - Add `UnversionedFixture<U> extends EntityFixture<U>` with `U withExtensionVersion(URI id, String version)`, an entity of a type that is not a `VersionedEntity`, carrying `version` as an unknown (extension) property. Expose it like `referenceFixture()` as an optional `unversionedFixture()` on the contract test. Add a case where both `findReference` and `findReferences` report `''` for such an entity. Implement it in `product-catalog/src/test/.../storage/` with a non-versionable type the module can store, for example `Product` from `product-shared-models` (check that it keeps unknown properties through `Entity`).
  - `findReferenceReturnsIdAndStoredType` asserts the full record, version included.
  - Both `{NgsiLd,Postgres}ReferenceReadRepositoryContractIT` in `product-catalog/src/test/.../storage/` pick the new cases up.
- **Acceptance:** `mvn test -pl storage-api,common,storage-postgresql -am` passes. `mvn integration-test -pl product-catalog -Dit.test='*ReferenceReadRepositoryContractIT' -DskipTests` passes on the default broker, with `-Dbroker=scorpio`, and with `-Dbroker=postgresql`.

### Step 3: Enforce reference version semantics in `ReferenceValidationService`
Reject a local `*Ref` whose explicit `version` differs from the target's current version, and accept a `*Ref` with no version whatever the target's version is.

- **`common/.../validation/ReferencedEntity.java`**: add `@JsonIgnore default String getReferenceVersion() { return null; }`. Its one-line Javadoc says a null or empty version pins nothing.
- Override it (`@JsonIgnore @Override public String getReferenceVersion() { return getVersion(); }`) in the 14 `*Ref` classes that have a `version` field. That is 13 type names, and `ResourceSpecificationRef` exists twice: `common/.../domain/ConstraintRef.java`, `product-catalog/.../domain/ResourceSpecificationRef.java`, `product-shared-models/.../product/{CategoryRef,ProductOfferingPriceRef,ProductSpecificationRef}.java`, `resource-function-activation/.../domain/{ConnectionPointRef,ResourceFunctionRef}.java`, `resource-shared-models/.../resource/{ResourceCandidateRef,ResourceCategoryRef,ResourceSpecificationRef}.java`, `service-shared-models/.../service/{ServiceCandidateRef,ServiceCategoryRef,ServiceLevelSpecificationRef,ServiceSpecificationRef}.java`. `@JsonIgnore` keeps the getter out of both the stored document and the NGSI-LD mapping, like `getReferenceHref`. Check that a stored document of one such ref has no `referenceVersion` key.
- **`ReferenceValidationService`**:
  - `storedTypes` becomes a lookup keyed by id that returns the whole `StoredReference` (`collectMap(StoredReference::id, Function.identity())`).
  - In `resolves`, every branch that found a stored target also requires `versionMatches(ref, stored)`: the result is true when the ref version is null or empty, otherwise `refVersion.equals(stored.version())`. That is the `LOCAL` branch and the `EXTERNAL` branch when `stored != null`. Only the `EXTERNAL` skip (`stored == null`) stays version-agnostic. The metric scope stays as today (`external` for an external ref with a local target).
  - `getCheckingMono` keeps a single `NonExistentReferenceException`. It lists missing references as today and adds version mismatches as `id (version x, current y)` under a `Reference version mismatch:` prefix. To do this, `findUnresolved` (or a private variant) has to keep why each reference failed. Keep the public signatures. Use named format constants, not inline literals.
  - Update the class and method Javadoc (one line each) to state the version rule.
- **Tests**: `common/src/test/.../validation/ReferenceValidationServiceTest.java` gets parameterized cases (`@MethodSource`) for: ref version null, `""`, equal, different, case-different, a pinned ref against a target whose version is `''`, a pinned external ref with no local target (skipped), a pinned external ref whose id names a local entity with a different version (unresolved, metric `external`/`unresolved`), the same with a matching version (resolved), and a list with one mismatch among valid refs (exactly that ref is unresolved, there is one lookup, and the metric records `local`/`unresolved`). Use a test `ReferencedEntity` that carries a version.
- **Guard**: add a test that fails when a `RefEntity` subclass with a `getVersion()` getter does not override `getReferenceVersion()`. Put it next to `all-in-one/src/test/java/org/fiware/tmforum/RelationshipsReadFromPropertiesTest.java`, which already scans every `RefEntity` subclass, and reuse its class scan.
- **Acceptance:** `mvn test -pl common -am` passes, and `mvn test` passes for the modules that own the touched `*Ref` classes and for `all-in-one`.

### Step 4: Integration tests on both backends, existing-IT audit, documentation
Prove the acceptance criteria end to end on Orion-LD, Scorpio and PostgreSQL, and document that the schema is ready for versioning.

- **New IT** `product-catalog/src/test/java/org/fiware/tmforum/productcatalog/ReferenceVersionIT.java`. Model it on `ExternalReferenceIT` (`extends AbstractApiIT`, `@MicronautTest(packages = "org.fiware.tmforum.productcatalog", contextBuilder = FirstMatchConfigContextBuilder.class)`). Use a parameterized test over a ProductSpecification with version `1.0` and a ProductOffering that references it through `productSpecification`:
  - ref version absent → 201; ref version `1.0` → 201; ref version `2.0` → 400;
  - the same three on `PATCH /productOffering/{id}` → 200/200/400;
  - after `PATCH` sets the specification's version to `2.0`, a ref pinned to `1.0` → 400, a ref pinned to `2.0` → 201, and an unpinned ref → 201. This shows `PATCH` updates in place and the ref follows the current version;
  - the specification `GET` still returns one entity with the new version. No version-specific endpoint or query parameter exists.
  - Add one case for a pinned ref to a target whose version is unset. Use a `CategoryRef` → Category created without `version` (Category is versionable, its stored version is `''`), and expect 400 when the ref carries a version and 201 without one. A truly unversioned target type stores the same `''`, so the unit test's "target version `''`" case covers it.
  - Add one case for an external-scope ref (an `href` on a host in `references.external-hosts`, set with `@Property` as `ExternalReferenceIT` does) whose id names the local ProductSpecification: pinned to `2.0` while the target is `1.0` → 400, pinned to `1.0` → 201.
- **Sub-type IT** `resource-catalog/src/test/java/org/fiware/tmforum/resourcecatalog/ResourceSpecificationVersionIT.java`, set up like `ResourceSpecificationApiIT`: a `logical-resource-specification` created with version `1.0`, and a ResourceCandidate whose `resourceSpecification` ref names it. Pinned to `1.0` → 201, pinned to `2.0` → 400, unpinned → 201. This proves on every backend that a sub-type inherits versioning.
- **Audit the existing ITs**. Run the IT suites of the modules whose `*Ref` classes changed: `product-catalog`, `product-ordering-management`, `product-inventory`, `quote`, `resource-catalog`, `resource-function-activation`, `resource-inventory`, `service-catalog`, `service-inventory`, `agreement`, `all-in-one`. A test that now fails because its test data pins a version that differs from the target's, for example a generated example builder setting `version = "string"`, must be fixed in the test data: either align the version or drop it. Never weaken the rule. List every adjusted test in the PR description.
- **Docs**:
  - In the `## Schema` section of `storage-postgresql/README.md`, write: `version` holds the TMForum label of `VersionedEntity` types (`''` otherwise) and is updated in place by `PATCH`; rows written before this ticket are backfilled by `V3`; `revision` is always `1` and `is_current` always `true`; the table is ready for versioning, and keeping superseded versions is a future, PostgreSQL-only extension that needs no migration.
  - In the `## References` section of `storage-api/README.md`, add a short paragraph on `StoredReference.version` (`''` unless the stored type is in `VersionedEntity.VERSIONED_TYPES`, on every adapter) and the pin rule.
  - New `release-notes/RELEASE_NOTES_ENTITY_VERSIONING.md`, in the style of the existing ones: the reference version rule (also applied to an external ref whose id names a local entity), the 400 on mismatch, an unchanged API, the same behaviour on both backends, and the list of out-of-scope items from the ticket.
  - `AGENTS.md`: one line under Key Conventions about `VersionedEntity` and `getReferenceVersion()`.
- **Acceptance:** `mvn integration-test -pl product-catalog -Dit.test=ReferenceVersionIT -DskipTests` and `mvn integration-test -pl resource-catalog -Dit.test=ResourceSpecificationVersionIT -DskipTests` pass with the default broker, `-Dbroker=scorpio` and `-Dbroker=postgresql`. The audited modules' ITs pass on the default broker and on `-Dbroker=postgresql`. `mvn spotbugs:spotbugs` reports nothing new.

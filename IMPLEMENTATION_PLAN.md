# Implementation Plan: TMForum - DB Backend - External refs

## Overview
References can point at entities held by another TMForum deployment. Since #178 (`anyMatch` → `allMatch`), `ReferenceValidationService` rejects every such entity, because it resolves all references against local storage. This plan makes the combination semantics explicit and adds a config-driven local/external classification: local references are validated strictly, external ones are skipped (no HTTP call) and counted. It also makes the read path tolerate unresolvable relationship targets and documents the policy in `common/README.md`. Steps 1–2 live in `common`'s validation layer and are backend-agnostic, so the PostgreSQL adapter (ticket 6) inherits them unchanged. Step 3 changes `BrokerBackedEntitiesRepository`, the broker adapter. **Hand-off to ticket 6:** the PostgreSQL `EntitiesRepository.getEntities` must give the same guarantees: return one entity per requested id, with a `TolerantEntityVOMapper.unresolvedTarget(id)` stub for each id that does not exist (otherwise the mapper drops list entries again), and return an empty list for empty input. Its `ReferencesRepository` must also implement Step 2's type-agnostic `findReference(id)`. Reusing Step 3's parameterized `BrokerBackedEntitiesRepositoryTest` cases against that adapter keeps the two in line.

### Decisions (binding for all steps)
- **Classification is an operator allow-list and is never inferred.** A reference is EXTERNAL only if its id starts with a configured id prefix, or its `href` starts with a configured href prefix. Everything else is LOCAL. Both lists default to empty, which keeps today's strict behaviour. A foreign host in a client-supplied `href` does **not** make a reference external on its own, because then any client could switch validation off. With the allow-list, a client can at most declare a reference as held by a deployment the operator already trusts.
- **External references are skipped.** They get no existence check and no outbound HTTP call to the other deployment (the ticket's recommendation). Each one is counted by a metric and debug-logged.
- **Href-only external references get a local type guard.** A reference that is external by its href prefix but not by its id prefix is looked up by id in *local* storage on write (one local call, none to the other deployment). If no local entity has that id, the reference is skipped as external. If one exists with an accepted type, it counts as a resolved local reference. If one exists with any other type, the reference is unresolved and the request fails with 400. Without this, a client could put a trusted href on the id of a local entity of another type (e.g. a `category` reference to a local `product-offering` id). Write validation would skip it, and the read path, which fetches href-only references locally (see below), would then build a `CategoryRef` from the wrong entity. References that match the id prefix are never looked up.
- **Id prefixes must not overlap the local id namespace.** A prefix as broad as `urn:ngsi-ld:category:` makes every local category reference external. It is skipped on write and read back id-only although the target exists locally, and nothing fails. The README says prefixes must be deployment-specific (e.g. `urn:ngsi-ld:category:partner-a-`). `ReferenceClassifier` logs a startup warning for any configured id prefix that is `urn:ngsi-ld:<type>:` or shorter, or continues it with only UUID characters (which overlap server-generated ids). Blank prefixes are dropped, because they would match everything.
- **Local references use `all` semantics.** Every non-null local reference must resolve with an accepted type. If one does not, the request fails with `NonExistentReferenceException`, which controllers map to 400 `INVALID_RELATIONSHIP`. The message names the unresolved ids.
- **Empty input passes.** A list that is empty, all-null or all-external validates to `true`. Today `Mono.zip` over an empty iterable completes *empty* rather than `true`. That silently empties the caller's chain, and step 1 fixes it.
- **Config lives in a new `ReferenceProperties` class** (`@ConfigurationProperties("references")`), not in `GeneralProperties`. The epic is shrinking `GeneralProperties`, which is mostly broker dialect.
- **Read path.** Relationships whose `@AttributeSetter` lacks `fromProperties = true` are fetched on read (e.g. `ProductOffering.category`, `Customer.engagedParty`). Two places fail when a target is missing:
  - `BrokerBackedEntitiesRepository.getEntities` uses `Mono.zip`, so one missing target empties the whole relationship map.
  - `mapping.strictRelationships` (ngsi-ld-java-mapping `MappingProperties`) defaults to `true`, so `EntityVOMapper.getObjectFromRelationship` then throws `MappingException`.

  Step 3 skips external ids, tolerates missing targets and sets `mapping.strictRelationships: false` in every module (`document-management` and `data-migrator` already do). Non-strict mode is confirmed in the 1.6.31 sources: for a target missing from the `getEntities` map, `getObjectFromRelationship` calls `targetClass`'s `String` constructor with the relationship object (e.g. `new CategoryRef(id)`). The entry is kept with its id set and is not dropped. The relationship's sub-properties are not merged on that path. A `targetClass` without a `String` constructor fails with `MappingException("Was not able to instantiate ... with a string parameter")` (the mapper calls `getDeclaredConstructor(String.class)`). A source scan of every non-`fromProperties` relationship found nine target classes that only declare `(URI id)`: `ServiceCandidateRef`, `ServiceCategoryRef`, `ResourceCategoryRef`, `ServiceLevelSpecificationRef`, `AssociationSpecificationRef`, `ServiceSpecificationRelationship`, `EntitySpecificationRelationship` (service- and resource-shared-models) and `org.fiware.tmforum.customer.AccountRef`, `PaymentMethodRef` (customer-shared-models). Examples are `ProductOffering.serviceCandidate`, `ResourceCandidate.category`, `UsageSpecification.entitySpecRelationship` and `PartyRole.account`/`paymentMethod`. `Customer` uses the same two customer classes with `fromProperties = true`, which is why they look safe there. Step 3 adds the missing `String` constructors and a guard test, so every fetched relationship target can be built id-only. The guard test, not this list, is the source of truth. **Known limitation, to be recorded in the README:** on those fetched relationships, the `href`/`name`/`@referredType` of an external reference therefore do not round-trip until ticket 5 stores the reference payload inline (`fromProperties = true`). Relationships that already use `fromProperties = true` (e.g. `Catalog.category`) round-trip fully today.
- **Needs explicit reviewer sign-off: the global switch to `strictRelationships: false`.** It is a behaviour change for *local* references too. A dangling local reference (target deleted after the write) reads back id-only instead of failing the GET with a `MappingException`. The alternative, keeping strict mode and only skipping external ids, would still fail the GET for every href-only external reference (see Step 3) and for every dangling local one.
- **The read path only sees ids.** The mapping library's `getEntities(List<URI>)` gets no `href`, so on read only the id-prefix list can skip the broker GET. A reference that is external only by its href prefix is still fetched from the local broker. A 404 becomes `Mono.empty()` and the reference reads back id-only. Any other broker error (e.g. a 400 for an id the broker rejects) raises `NgsiLdRepositoryException` and fails the whole GET. This is deliberate: swallowing arbitrary broker errors would hide real outages. In practice the broker already accepted the id as a relationship object on write, so a GET with it should not be rejected. Operators whose external ids are predictable should set the id prefix as well. The README records this. The write-side type guard above keeps a wrong-typed local entity off this path. A later local entity with the same id would need a client-chosen id, but ids are server-generated (`urn:ngsi-ld:<type>:<uuid>`).

## Steps

### Step 1: Make the combination semantics explicit in `ReferenceValidationService`
Files:
- `common/src/main/java/org/fiware/tmforum/common/validation/ReferenceValidationService.java`
- new `common/src/test/java/org/fiware/tmforum/common/validation/ReferenceValidationServiceTest.java`

Changes:
- Replace the `Mono.zip(..., allMatch)` with a combinator that is well defined on empty input. Add a method returning the unresolved references, e.g. `Mono<List<T>> findUnresolved(List<T> refs)` built with `Flux.fromIterable(refs).filter(Objects::nonNull).flatMapSequential(ref -> exists(ref).filter(b -> !b).map(b -> ref)).collectList()`. `flatMapSequential` keeps today's concurrency and emits in input order, so the error message is deterministic. `checkReferenceExists` becomes `findUnresolved(...).map(List::isEmpty)`, so its public signature and semantics stay the same. A null `refs` list counts as empty.
- `getCheckingMono` fails with `NonExistentReferenceException("References do not exist: [<ids>]")`, listing only the unresolved entity ids rather than the whole `toString` of every reference. The existing Javadoc should say "all", which matches `TmForumExceptionHandler`'s "At least one of the references does not exist".
- Unit test (JUnit 5 + Mockito, mocked `ReferencesRepository`). Use a `@ParameterizedTest` with a `@MethodSource` over these cases: empty list → true; only nulls → true; one resolves → true; all resolve → true; one of three missing → false (the #178 regression); wrong type (repository returns empty) → false; all missing → false. Add one test asserting that the `getCheckingMono` error message contains exactly the missing ids, in input order.

Acceptance: `mvn test -pl common -Dtest=ReferenceValidationServiceTest` passes, and `mvn test -pl common` stays green.

### Step 2: Local/external classification, skip external references, meter them
Files (in `common` unless a path says otherwise):
- new `configuration/ReferenceProperties.java`: `@ConfigurationProperties("references")`, Lombok `@Data`, `List<String> externalIdPrefixes = List.of()` and `List<String> externalHrefPrefixes = List.of()`. Env vars are `REFERENCES_EXTERNAL_ID_PREFIXES` and `REFERENCES_EXTERNAL_HREF_PREFIXES` (comma-separated).
- `validation/ReferencedEntity.java`: add `@JsonIgnore default URI getReferenceHref() { return null; }`. It is deliberately not named `getHref`, so the Jackson and mapping annotations on `RefEntity.getHref()` are not affected.
- Override `getReferenceHref()` to return `getHref()` (the getter, not the field) in every `ReferencedEntity` implementation that has an `href` field, otherwise `references.external-href-prefixes` silently does nothing for it:
  - `common/.../domain/RefEntity.java`. Calling the getter matters: `usage-management`'s `UsageSpecificationRef` redeclares its own `href` field and Lombok accessors, so `RefEntity.href` stays null for it.
  - `common/.../domain/ReferenceValue.java` (covers `ProductOfferingRefValue`, `RelatedPartyRefValue`)
  - `product-shared-models/.../ProductRefOrValue.java`
  - `product-shared-models/.../ProductOfferingQualificationItemRef.java`
  - `resource-shared-models/.../Resource.java`
  - `service-inventory/.../domain/ServiceRefOrValue.java`

  Re-check the list with `grep -rl --include=*.java ReferencedEntity . | xargs grep -l 'URI href'`, and look for subclasses of the listed classes that redeclare `href` (today only `UsageSpecificationRef`). Mark each override `@JsonIgnore` like the interface default, so no new field is serialized.
- new `validation/ReferenceScope.java`: an enum with `LOCAL` and `EXTERNAL`.
- new `validation/ReferenceClassifier.java`: a `@Singleton` with `ReferenceScope classify(ReferencedEntity ref)` and a convenience `boolean isExternal(URI id)` for the read path (step 3). It does plain `String.startsWith` matching on `id.toString()` and `href.toString()`. A null id or href is not matched. On construction it trims every configured prefix and drops blank entries with a WARN, because `startsWith("")` is always true and an empty env var or trailing comma would otherwise turn validation off. Add a one-line Javadoc that states the allow-list rule. `classify` also tells apart the two EXTERNAL cases the service treats differently (e.g. `isExternalById(ref)` or a third enum value `EXTERNAL_BY_HREF`; pick whichever keeps the service simplest). On construction it also logs a WARN for each id prefix that can overlap server-generated local ids (`urn:ngsi-ld:<type>:<uuid>`): a prefix of `urn:ngsi-ld:` itself (e.g. `urn:`), or a match of a named-constant pattern such as `^urn:ngsi-ld:[^:]*(:[0-9a-fA-F-]*)?$` (type only, or type plus a UUID-like start such as `urn:ngsi-ld:category:a1`).
- `repository/ReferencesRepository.java`: add `Mono<EntityVO> findReference(String id)`, which returns the entity regardless of type, or empty. `BrokerBackedReferencesRepository` implements it as `retrieveEntityById(URI.create(id))`, and `referenceExists` becomes `findReference(id).filter(...)`.
- `validation/ReferenceValidationService.java`: inject `ReferenceClassifier` and a `MeterRegistry`. Make the registry optional (explicit constructor with `@Nullable MeterRegistry`) so that contexts with metrics disabled still start. References external by id prefix are filtered out before any repository call, counted, and debug-logged with the id. Href-only external references go through `findReference`: empty → skipped as external, accepted type → resolved local, other type → unresolved (see the type-guard decision). Count with a `Counter` named in a constant, e.g. `REFERENCES_METRIC = "tmforum.references"`. Tags are `scope` (`local`|`external`) and `result` (`resolved`|`unresolved`|`skipped`). Keep tag values as constants, with no ids in tags (cardinality).
- Tests:
  - new `ReferenceClassifierTest`: parameterized over the id-prefix match, the href-prefix match, no match, null href, empty config, a foreign-host href that is not in the allow-list (→ LOCAL), one non-`RefEntity` implementation (e.g. `ReferenceValue`) matched by its href prefix (→ EXTERNAL), a `UsageSpecificationRef` matched by its href prefix (→ EXTERNAL, guards the shadowed field), and a config holding a blank entry next to a real prefix (→ the blank is ignored, an unmatched reference stays LOCAL). One more parameterized test checks the startup warning: `urn:`, `urn:ngsi-ld:category:` and `urn:ngsi-ld:category:a1` log it, and `urn:ngsi-ld:category:partner-a-` does not.
  - extend `ReferenceValidationServiceTest`: a mixed list of one local-existing and one id-prefix external entry → true, with the repository never called for the external one (`verify(..., never())`); one local-missing plus one external → false; all external → true. Href-only external cases: no local entity → true; local entity with an accepted type → true; local entity with another type → false. Use `SimpleMeterRegistry` to assert the counter values per tag.

Acceptance: with empty config, behaviour is identical to step 1. `mvn test -pl common` passes, and `mvn clean install -DskipTests -DskipITs` compiles all modules.

**As implemented (plan update):**
- Step 2 classifies by href host, not by id prefix, so `getEntities` has no id-based skip. It fetches every id with `flatMapSequential`, a 404 becomes an unresolved-target stub (read back id-only, see the multi-entry bullet below), and any other broker error fails the read. The ticket-6 hand-off in the Overview reflects this.
- MapStruct rejects two public single-argument constructors as ambiguous. The `URI` constructors are therefore marked with the new `common/.../mapping/Default` annotation (MapStruct honours any annotation named `Default`, and 1.6.3 ships none).
- The guard test also flagged three setters without a `targetClass` (`Object`, so they could never be read when non-empty): `AgreementSpecification.relatedParty`/`specificationRelationship` and `ResourceCategory.parentId`. They now name their field's element class.
- **Multi-entry lists (fixed in the PR #4 review):** `EntityVOMapper.zipToList` (1.6.31) silently drops every list entry missing from the `getEntities` result, for lists of two or more entries. `getEntities` therefore returns a stub (`TolerantEntityVOMapper.unresolvedTarget(id)`) for each 404 target instead of omitting it. `common/.../mapping/TolerantEntityVOMapper` (`@Replaces(EntityVOMapper.class)`) maps a stub as an entity of the target class's type that carries only the relationship's own sub-properties. A target class without `@MappingEnabled` (e.g. `ServiceCandidateRef`, customer `AccountRef`) is built id-only through its `String` constructor, like the library's non-strict path, so the `String`-constructor guard test stays sufficient. Unresolved targets therefore read back id-only in lists of any length. A single relationship also keeps the sub-properties stored on it (e.g. `name`), and list entries get none, because `zipToList` does not merge them. In strict mode a stub fails the mapping, as the library does. Step 4 may use multi-entry lists. The mapper subclass can go once the library builds unresolved list entries itself.

# Implementation Plan: TMForum - DB Backend - Extract Repo

## Overview
Put a storage-neutral port in front of persistence. It lives in a new `storage-api` Maven module and is split into read and write interfaces, with a neutral reference type and neutral error semantics. Today's NGSI-LD code (`TmForumRepository`, `NgsiLdBaseRepository`, `BrokerBackedReferencesRepository`) becomes the adapter that implements the port. Controllers and services then depend only on the interfaces. Both backends are permanent (decision 7), so the port is a documented, tested public contract. The ticket ships with **zero behaviour change**: the ITs and the HTTP responses stay byte-identical.

### Facts from the survey (main @ `f63b9b42`)
- `TmForumRepository` (`@Singleton`, extends `NgsiLdBaseRepository`) is referenced by 6 main files in `common` and by about 65 files in the 20 API modules. All of the module files are controllers, and they pass it to the `AbstractApiController`/`AbstractSubscriptionApiController` super constructors. 19 classes extend `AbstractSubscriptionApiController`. `all-in-one` compiles the module sources through `build-helper-maven-plugin` and has no references of its own. `data-migrator` does not use it.
- The only callers of `extractTotalCount` are in `common/src/test/.../TmForumRepositoryTest.java`. It stays package-private inside the adapter.
- `ReferencesRepository.referenceExists`/`findReference` return `Mono<EntityVO>`. They are used only by `ReferenceValidationService`, which reads `getType()`. Their result comes from the `@Cacheable` `retrieveEntityById` (`Mono<EntityVO>`), so the cached value must stay `EntityVO` and be mapped to the neutral type *after* the cache.
- The broker leaks through the errors: `AbstractApiController.create`/`patch` and the dead `AbstractSubscriptionApiController.create(Subscription)` switch on `HttpClientResponseException` status (CONFLICT/BAD_REQUEST/other). `NgsiLdBaseRepository` throws `DeletionException` (NOT_FOUND/UNKNOWN), `NgsiLdRepositoryException` and `TmForumException`. When an unmapped `HttpClientResponseException` reaches `HttpClientExceptionHandler`, the client gets a 502.
- Port calls also happen outside `common`, with no error mapping of their own: `party-catalog` `OrganizationApiController.deleteOrganization` calls `deleteDomainEntity` (it relies on the adapter's `DeletionException`), and the `resource-catalog`, `resource-inventory` and `software-management` controllers call `updateDomainEntity` directly (a raw broker error reaches the client as 502). That is why Step 3 renders errors in a handler instead of at each call site.
- Only `AbstractSubscriptionApiController` uses the subscription methods `createSubscription(SubscriptionVO, String)`, `retrieveSubscriptionById` and `deleteDomainSubscriptionByTmForumSubscription`, all on its inherited `repository` field (it has no repository field of its own). They are NGSI-typed, and ticket 1 owns them, so they stay **out of** the entity port.
- `AbstractSubscriptionApiController.create(Subscription)` is `private` and never called, so it is dead, and so is `NgsiLdBaseRepository.createDomainSubscription`, which only it calls. The live path is `create(TMForumSubscription)`: the duplicate check (`findEntities`, TF-UNKNOWN 500 on failure), then `createSubscription` (raw broker errors, uncaught, 502), then `AbstractApiController.create` for the `TMForumSubscription` entity.
- The two update modes already differ on an emptied list: the append path writes `[]`, which reads back as an empty list; the replace path sends NGSI-LD Null, which deletes the attribute, so it reads back absent.
- There are 73 `*IT.java` files; the ticket text says 72. All of them must pass.
- CI builds `common` with explicit lists such as `--projects common,...-shared-models,...` (`.github/workflows/test-brokers.yaml`, `conformance-test.yaml`, and `README.md`). Those lists must gain `storage-api`, or the reactor cannot resolve it.

### Port shape (target, package `org.fiware.tmforum.storage`)
```java
public interface EntityReadRepository {
    <T> Mono<T> get(URI id, Class<T> entityClass);
    <T> Mono<PagedResult<T>> findEntities(Integer offset, Integer limit, Class<T> entityClass,
                                          String query, String ids, String types, String orderBy);
    default <T> Mono<PagedResult<T>> findEntities(Integer offset, Integer limit, String entityType,
                                                  Class<T> entityClass, String query) { /* delegates */ }
    <T> Mono<PagedResult<T>> findEntitiesPolymorphic(Integer offset, Integer limit, String types, String query,
                                                     String ids, String orderBy,
                                                     Function<String, Class<? extends T>> typeToClass);
}
public interface EntityWriteRepository {
    <T> Mono<Void> createDomainEntity(T domainEntity);
    <T> Mono<Void> updateDomainEntity(String id, T domainEntity);
    Mono<Void> deleteDomainEntity(URI id);
}
public interface EntityRepository extends EntityReadRepository, EntityWriteRepository {}
public interface ReferenceReadRepository {
    Mono<StoredReference> referenceExists(String id, List<String> acceptedTypes);
    Mono<StoredReference> findReference(String id);
}
public record StoredReference(String id, String type) {}
public record PagedResult<T>(List<T> items, Integer offset, Integer limit, Integer totalCount) {}  // moved from common
public class StorageException extends RuntimeException { StorageErrorReason reason(); StorageOperation operation(); }
public enum StorageErrorReason { NOT_FOUND, CONFLICT, INVALID_DATA, PARTIAL_UPDATE, UNAVAILABLE, UNKNOWN }
public enum StorageOperation { READ, LIST, CREATE, UPDATE, DELETE }
```
The method signatures are today's, kept verbatim to keep the rewiring mechanical. The only changes are the `EntityVO` → `StoredReference` swap and the default-method overload. `StorageOperation` names the backend step that failed. Together with the reason, it is the only signal `common` uses to render today's responses (Step 3), so no rendering decision depends on the type of the cause. `query`/`orderBy` remain the `QueryParser` output (NGSI-LD q syntax). That is documented as transitional coupling, which ticket 7 removes, so do not change `QueryParser` here.

### Open parity questions (for tickets 0 and 6)
- Update of an absent id fails with a different operation per NGSI-LD mode: append is (UPDATE, NOT_FOUND), rendered TF-UNKNOWN 500 "Unspecified downstream error" at the call site; replace fails at its pre-read, (READ, NOT_FOUND), rendered CA 500. This ticket keeps both (zero change). Ticket 6 must choose deliberately which body the PostgreSQL adapter reproduces; ticket 0 records the choice. This replace-mode pre-read (READ for an absent id or an error status, UPDATE for no answer) is the one recorded exception to the per-method operation contract (Step 1).

### Known NGSI-LD defects (found in Step 7, for ticket 0 / a bug)
All exist on `main` today and stay unchanged here (zero behaviour change). The port Javadoc marks them as NGSI-LD adapter defects, not contract rules, and the contract IT pins them through `KnownDeviation`, so a fix fails the pinned case instead of passing silently.
- `findEntitiesPolymorphic` with several ids and several types fails on Orion-LD with (LIST, UNKNOWN). The only production caller, `AbstractApiController.listPolymorphic`, always passes `ResourceTypeRegistry.ALL_SPEC_TYPES`/`ALL_RESOURCE_TYPES`, so on Orion-LD `GET /resourceSpecification?id=<a>,<b>` (resource-catalog, software-management) and `GET /resource?id=<a>,<b>` (resource-inventory, software-management) return TF-UNKNOWN 500.
- On Orion-LD in append mode (the default IT and production setting), an update that empties a list whose instances carry a datasetId (e.g. a PATCH with `relatedParty: []`) leaves the entity unreadable: the broker keeps the instances and adds an empty one, so later reads fail.
- On both brokers, `findEntities` completes empty instead of emitting a page when the page holds no entity (nothing matches, or the offset is past the last match, with totalCount > 0): `zipToList` zips zero sources. The list endpoints then still answer 200 `[]`, but `AbstractApiController.list` sets no pagination attributes, so e.g. `GET /catalog?offset=<past end>` carries no `X-Total-Count`/`Link` headers. `findEntitiesPolymorphic` already emits the empty page. The contract requires a page (a PostgreSQL adapter must emit one); the IT pins the deviation as `EMPTY_PAGE_COMPLETES_EMPTY`.
- Replace mode is never contract-tested against a live broker: the failsafe `argLine` pins `general.replace-on-update=false` for every IT (Scorpio 5.0.3 in the test cluster does not create attributes with PATCH /attrs). Only the mocked Step 3 tests cover it.

## Steps

### Step 1: Create the `storage-api` module with the documented port types
- Add `storage-api/pom.xml` (artifact `storage-api`, parent = root). Its only compile dependency is `io.projectreactor:reactor-core`, version managed by the Micronaut BOM, and its tests use `junit-jupiter`. Add a `maven-enforcer-plugin` `bannedDependencies` rule that bans `io.github.wistefan:*`, `io.micronaut*:*` and `org.fiware.tmforum:*` from this module. That makes "no NGSI-LD/framework types in the port" a build failure instead of a convention. If the enforcer plugin is not yet in the root `pluginManagement`, add its version as a root property.
- Register `<module>storage-api</module>` in the root `pom.xml` **before** `common`. Add the `storage-api` dependency (`${project.version}`) to `common/pom.xml`.
- Create the types listed under *Port shape* in `storage-api/src/main/java/org/fiware/tmforum/storage/`: `EntityReadRepository`, `EntityWriteRepository`, `EntityRepository`, `ReferenceReadRepository`, `StoredReference`, `PagedResult`, `StorageException`, `StorageErrorReason`, `StorageOperation`, plus a `package-info.java`.
- Move `PagedResult` from `common/.../repository/PagedResult.java` to the new package and update every import in `common`. No module outside `common` imports it.
- The Javadoc is the contract, so it is denser than the rest of the repo by design. Keep each item short and cover only what the signature cannot show:
  - `get`: returns empty, not an error, when the id is unknown, has no type segment (`urn:ngsi-ld:<type>:…`), or its type segment is not one the class is persisted as (today `@MappingEnabled.entityType`; name the annotation in prose and do not depend on it). The check is on the id's type segment, not on the stored type, as in the NGSI-LD adapter and `ResourceTypeRegistry.extractTypeFromId`; every adapter applies the same rule. A class the backend cannot persist (today: no annotation) fails synchronously with `IllegalArgumentException`, rendered as the CA 400.
  - `findEntities`/`findEntitiesPolymorphic`: `types` and `ids` are comma-separated with OR semantics. `query`/`orderBy` are `QueryParser` output (transitional, ticket 7). `totalCount` is null when the backend cannot report it. `typeToClass` receives the stored type.
  - `updateDomainEntity`: writes only the attributes the entity carries (null fields are untouched; an emptied list is cleared and reads back either absent or as an empty list, callers must accept both), never a whole-document overwrite. Fails with `NOT_FOUND` when the id is absent and never creates or completes silently, because `AbstractApiController.relatedEntityHandlingMono` relies on that failure for its update-else-create. Its failures carry UPDATE, except the recorded NGSI-LD replace-mode pre-read (see *Open parity questions*). Fails with `PARTIAL_UPDATE` when the backend wrote only some attributes.
  - `createDomainEntity`: `CONFLICT` when the id exists, `INVALID_DATA` when the backend rejects the content.
  - `deleteDomainEntity`: `NOT_FOUND` when the id is absent.
  - The interfaces carry the type-level notes: a `Mono<Void>` completes empty on success, failures are signalled as `StorageException` with a reason and the failing operation, and references are inline, so no foreign-key semantics apply. `UNAVAILABLE` means the backend gave no answer. `UNKNOWN` means it answered with an error that has no other reason. `StorageOperation` is part of the contract per method, because `common` renders the HTTP response from it: `get`/`findReference`/`referenceExists` → READ, `findEntities*` → LIST (also when a nested read fails), `createDomainEntity` → CREATE, `updateDomainEntity` → UPDATE, `deleteDomainEntity` → DELETE. The only recorded exception is the NGSI-LD replace-mode pre-read (*Open parity questions*). Callers branch on the reason, and only `common`'s error rendering reads the operation.
- Update the `--projects` lists in `.github/workflows/test-brokers.yaml` (both jobs), `.github/workflows/conformance-test.yaml` and `README.md` (conformance command) to include `storage-api`.
- Add unit tests in `storage-api/src/test/java`: parameterized tests for the `findEntities` default overload (it delegates with `ids=null`, `types=entityType`, `orderBy=null`, using a tiny in-test stub) and for `StorageException` reason, operation and cause propagation.
- **Acceptance:** `mvn clean install -DskipTests -DskipITs` is green. `mvn test -pl storage-api,common` is green. Nothing implements the port yet, so behaviour is unchanged.

### Step 3: Make error semantics storage-neutral (zero HTTP change)
Today's error responses depend on *where* a failure comes from, not only on the broker status. Every origin below keeps exactly its response. (`TF-x` = `TmForumExceptionHandler` with reason x, `DEL` = `DeletionExceptionHandler`, `CA` = the `CatchAllExceptionHandler` 500 body, `502` = the `HttpClientExceptionHandler` body. "Call site" = the `onErrorMap` in `AbstractApiController.create`/`patch` (the subscription controller reaches it for its `TMForumSubscription` entity), which covers the whole chain, so it includes the checking mono's reference validation and related-entity writes. "Uncaught" = every other caller, e.g. `OrganizationApiController.deleteOrganization` and the module controllers that call `updateDomainEntity` directly.)

| Origin today | Thrown today | Response at call site / uncaught | New `StorageException` (operation, reason) |
|---|---|---|---|
| `get`/`retrieveEntityById`/`findReference`, non-404 or no answer | `NgsiLdRepositoryException` | CA 500 / CA 500 | READ, UNKNOWN or UNAVAILABLE |
| `findEntities*` failure, from `queryEntities` or from mapping the result (`zipToList` resolving relationships through `BrokerBackedEntitiesRepository.getEntities` → `retrieveEntityById`); today's `onErrorResume(t -> …)` catches everything | `TmForumException` UNKNOWN "Was not able to list entities." | TF-UNKNOWN 500 / same | LIST, UNKNOWN or UNAVAILABLE. LIST wraps **every** failure, a nested `StorageException` (e.g. READ from relationship resolution) included, and keeps the message "Was not able to list entities.". Do not let a nested READ pass through: it would render CA 500. |
| `deleteDomainEntity` 404 / other | `DeletionException` NOT_FOUND / UNKNOWN | DEL 404 / DEL 500 | DELETE, NOT_FOUND / UNKNOWN or UNAVAILABLE |
| create, broker 409 / 400 / other status | raw `HttpClientResponseException` | TF-CONFLICT / TF-INVALID_DATA / TF-UNKNOWN "Unspecified downstream error" ; uncaught 502 | CREATE, CONFLICT / INVALID_DATA / UNKNOWN (404 → NOT_FOUND, mapped like UNKNOWN) |
| create, no answer | raw `HttpClientException` | 502 / 502 (call site passes it through) | CREATE, UNAVAILABLE |
| update append path (`patchEntity`) and replace path `updateAttributes`, broker 409 / 400 / 404 / other | raw `HttpClientResponseException` | as create, "updating" wording / 502 | UPDATE, CONFLICT / INVALID_DATA / NOT_FOUND / UNKNOWN |
| update, no answer | raw `HttpClientException` | 502 / 502 | UPDATE, UNAVAILABLE |
| update replace path, pre-read 404 ("Entity … does not exist.") or other status | `NgsiLdRepositoryException` | CA 500 / CA 500 | READ, NOT_FOUND / UNKNOWN (the failing step is the read) |
| update replace path, pre-read no answer (the pre-read only catches `HttpClientResponseException`) | raw `HttpClientException` | 502 / 502 | UPDATE, UNAVAILABLE (not READ: READ always renders CA 500, which `get` with no answer needs) |
| update replace path, broker 207 | `TmForumException` INVALID_DATA "Not all attributes could be updated: …" | TF-INVALID_DATA 400 (passed through) / same | UPDATE, PARTIAL_UPDATE, same message |

They assert **only** the HTTP status and the `ErrorDetails` code/reason/message, never the exception type, so they stay unchanged and green through the whole step. The real `TmForumRepository`, `ReferenceValidationService` and handler beans are in the context. The broker side is `@MockBean` `EntitiesApiClient`/`EntityAttributesApiClient`/`SubscriptionsApiClient` returning `Mono.error(new HttpClientResponseException(msg, HttpResponse.status(s).body(problemJson)))` for status `s`, `Mono.error(new HttpClientException(...))` for no answer, and a 207 response for the partial update. Requests go through the injected `HttpClient`; assert on the `HttpClientResponseException` it raises (status + `ErrorDetails` body).
  - Update modes: a second test class (subclass with its own `TestPropertyProvider`) per `general.replaceOnUpdate` value, since the property is fixed per application context.
  - Module cases (party-catalog, resource-catalog) use the same harness in their module, with `@MicronautTest(packages = ...)` on the real module controller.
  - Cover every table row, parameterized:
    - {create, patch, delete, list, retrieve} × {broker 400, 404, 409, 500, no answer} for the final port call.
    - The same create/patch status set when the failure comes from the checking mono: reference validation (`findReference` failing → CA 500) and the related-entity write in `relatedEntityHandlingMono` (update fails, then the fallback create fails with 409 / 400 / 500 / no answer).

    - A related-entity lookup (relationship resolution through `BrokerBackedEntitiesRepository`) failing with a broker 500 and with no answer: during list → TF-UNKNOWN 500 "Was not able to list entities.", during get/retrieve → CA 500.
    - Both update modes (`replaceOnUpdate` false and true), including the pre-read 404 → CA 500, the pre-read 500 → CA 500, the pre-read with no answer → 502, and the 207.

    - A direct, uncaught `updateDomainEntity` caller (e.g. `resource-catalog` `ResourceSpecifcationApiController`) → 502.
    - `party-catalog`: a new `OrganizationApiControllerTest` with delete 404 → DEL 404 and delete 500 → DEL 500.

For a broker that answered, the message is exactly today's `responseBody`, i.e. `e.getResponse().getBody(String.class).orElse(e.getMessage())`, because the call site interpolates it into the TF message. Elsewhere it is today's message. The original exception is the cause, kept for logging only. `NgsiLdRepositoryException` and the adapter's `DeletionException`/`TmForumException` throws are replaced, except on the subscription-API path (`SubscriptionRepository`, ticket 1): `deleteDomainSubscription` keeps `DeletionException` and `retrieveSubscriptionById` keeps `NgsiLdRepositoryException`.
- Existing adapter unit tests that assert today's exception types are rewritten to assert the `StorageException` operation, reason and message from the table. These are the only existing assertions this step may change, and the characterization tests must not change:
  - `NgsiLdBaseRepositoryUpdateTest`: `anUnknownEntityIsAnError` (`NgsiLdRepositoryException` → READ, NOT_FOUND), `aMultiStatusAnswerIsAnError` and `aMultiStatusAnswerRaisedAsExceptionIsAnError` (`TmForumException` INVALID_DATA → UPDATE, PARTIAL_UPDATE, same message), `aBrokerErrorIsPropagated` (raw 400 → UPDATE, INVALID_DATA, message = response body). `aMultiStatusAnswerCompletesTheCacheInvalidatingWrite` and `aNoContentAnswerRaisedAsExceptionIsASuccess` stay as they are: the 207 still completes `updateAttributes` so `@CacheInvalidate` fires, and the translation happens around it.
  - `BrokerBackedEntitiesRepositoryTest.getEntities_brokerErrorPropagates` (`NgsiLdRepositoryException` → READ, UNKNOWN).
  - Add the cases the table needs that no test has yet, parameterized: LIST, DELETE and CREATE failures with a broker status and with no answer.
  - Unchanged: `NgsiLdBaseRepositoryAppendUpdateTest` and `TmForumRepositoryTest` assert no exception types. The `TmForumException` assertions in `AbstractApiControllerTest` (pagination validation) and `AbstractSubscriptionApiControllerTest` (duplicate CONFLICT) come from the controller, not the adapter.
- In `common`, render it back:
  - Call site: switch only on `StorageException` with operation CREATE/UPDATE and reason CONFLICT/INVALID_DATA/NOT_FOUND/UNKNOWN (the backend answered with an error), with NOT_FOUND and UNKNOWN both mapping to the "Unspecified downstream error" case. `operation` only decides *whether* the call site maps; the wording and log line come from the call site, as today. `create` keeps "…on creating…" and its "Broker rejected the entity creation…" log line, `patch` keeps "…on updating…" and no log line, also when the failure is the (CREATE, CONFLICT) of the related-entity fallback create. Everything else passes through unchanged, as it does today.
  - A new `StorageExceptionHandler` renders every `StorageException` that is not mapped, keyed on (operation, reason) only: DELETE → DEL 404 for NOT_FOUND, otherwise DEL 500. LIST → TF-UNKNOWN 500 with the stored message. READ → CA 500. CREATE/UPDATE → TF-INVALID_DATA 400 with the stored message for PARTIAL_UPDATE, otherwise 502. To keep the bytes and log lines identical it injects the four existing handler beans and delegates, leaving those classes untouched: `deletionExceptionHandler.handle(request, new DeletionException(msg, e, NOT_FOUND|UNKNOWN))`, `tmForumExceptionHandler.handle(request, new TmForumException(msg, e, UNKNOWN|INVALID_DATA))`, `catchAllExceptionHandler.handle(request, e)` (a `StorageException` is not an `IllegalArgumentException`, so it gets the 500 body) and `httpClientExceptionHandler.handle(request, new HttpClientException(msg, e))`. Its Javadoc carries the table in one short line per operation.
  - `AbstractApiController.delete` needs no mapping. The handler covers it and `OrganizationApiController.deleteOrganization` alike.
- After this step, no code in `common` outside `common/.../repository` may inspect `HttpClientResponseException` that came from a port call. `BrokerRequestLoggingFilter` and `AbstractApiIT` are not port callers and stay as they are.
- If any case cannot be kept identical, stop and report it as a blocker instead of accepting a deviation. Accepted deviations must be recorded in ticket 0.
- **Acceptance:** the characterization tests are unchanged and green, `mvn test -pl common,party-catalog,resource-catalog` is green, and `mvn integration-test -pl product-catalog,party-catalog` is green.
